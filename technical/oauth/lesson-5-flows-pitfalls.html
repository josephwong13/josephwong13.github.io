Other Flows & Common Pitfalls

Lesson 2 covered the authorization code flow — the workhorse. But there are three other grants you may encounter in RFC 6749: client credentials (M2M), implicit (now deprecated), and resource owner password credentials (also deprecated). Lesson 5 covers when each is appropriate, plus the security pitfalls RFC 9700 explicitly addresses — most of which you'll meet in real MCP and OAuth deployments.

The grant-type landscape

GrantWhen it's usedStatus
authorization_code User is present. Browser hands a code to the client (Lesson 2). Default. Always. With PKCE.
client_credentials No user — a backend service authenticating itself. Legitimate use case.
refresh_token Swap a refresh token for a new access token (Lesson 3). Companion to authorization_code.
implicit (response_type=token) Legacy SPAs that returned tokens in the URL fragment. Deprecated. Don't use.
password Legacy first-party apps that collected the user's password directly. Deprecated. Don't use.

Client credentials — when the user is a service

Use case

A CI pipeline needs to call your internal API. There's no human, no browser, no consent screen. The pipeline authenticates with its own client ID + secret at /token, gets an access token back, and uses it.

POST https://auth.internal/oauth/token
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials
&client_id=ci-pipeline
&client_secret=***
&scope=build:write

This grant is the right tool for M2M. The "user" is the service itself; consent is implicit in the deploy.

MCP · Could a server-to-server use this?

Yes. An MCP server running as the data owner (rather than holding data on behalf of users) could mint tokens via client_credentials for downstream services that call it. client_id_metadata_document_supported in AS metadata signals whether the modern alternative is available. [R9]

Implicit — deprecated, do not use

Why implicit is dead

The implicit grant returned access tokens in the URL fragment. The browser history, referer headers, JS-injected tracking pixels, and extensions all saw that token. RFC 9700 formally deprecates it: "Clients SHOULD NOT use the implicit grant... unless access token injection in the authorization response is prevented and the aforementioned token leakage vectors are mitigated." [R2]

OAuth 2.1 drops implicit entirely. The modern replacement is authorization code + PKCE — yes, even for SPAs. [R3]

RO password — deprecated, do not use

Why RO password is dead

The user types their password into the client. The client forwards it to the AS to mint a token. The whole point of OAuth — that the client never touches the password — is gone. RFC 9700 deprecates this except for "trusted first-party apps" and even then recommends migration. [R2]

Common pitfalls and the attacks they enable

Pitfall 1 · Open redirector on redirect_uri

An AS compares the registered redirect_uri with what the client sends. If your client uses a wildcard, prefix-match, or any non-exact comparison — or if it follows redirects on the redirect URI itself — an attacker can submit redirect_uri=https://yoursite.com/oauth/callback?next=https://evil.com and exfiltrate the authorization code via a chained redirect. RFC 9700 mandates exact string matching for redirect URIs. [R2]

Pitfall 2 · Missing or weak CSRF protection

If the authorize request sends no state (and no PKCE / nonce), an attacker can trick a logged-in user's browser into starting an OAuth flow that returns the code to the attacker's account. This is "login CSRF". Mitigation: always set state, always use PKCE. [R2]

Pitfall 3 · The confused deputy

A user with access to ten resources grants an OAuth client access to all ten — but only intended to grant access to one. The client legitimately uses the token to read resources the user didn't think about. The user's access is being delegated through a confused intermediary.

Mitigation: narrow scopes (Lesson 3), explicit consent screens, and (in MCP and similar) the resource parameter in the authorize request that binds tokens to a specific RS. [R8] [R9]

Pitfall 4 · Access tokens in URL fragments

Implicit grant leak. Use authorization code with PKCE.

Pitfall 5 · Sharing refresh tokens across devices

A single refresh token reused on phones, browsers, and laptops gives any one compromised device unlimited token minting. OAuth 2.1 says refresh tokens for public clients must be sender-constrained or one-time-use (rotation: server invalidates each refresh token after one exchange, returns a new one). [R3]

Pitfall 6 · Tokens in cookies or localStorage without care

An XSS bug = full token theft. Use HttpOnly, Secure cookies and CSRF tokens if you must put tokens there. Better: keep tokens in memory (JS variable) and use refresh tokens for persistence. [R2]

The MCP connection — discovery + registration

MCP · Bootstrapping without prior setup

MCP has to handle a special challenge: a brand-new MCP client (Claude Desktop) and a brand-new MCP server often have no prior relationship. No pre-registered client ID, no shared secret. The MCP spec layers three RFCs to handle this. [R9]

Step 1. Discover. The MCP client makes an unauthenticated request. The RS replies 401 with:

HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer resource_metadata="https://mcp.example.com/.well-known/oauth-protected-resource",
                         scope="files:read"

Step 2. Resolve. Client fetches that URL → Protected Resource Metadata (RFC 9728) → authorization_servers array → Authorization Server Metadata (RFC 8414) → finally the actual /authorize and /token endpoints. [R8] [R7]

Step 3. Register. If the client has no client_id, three options in priority order:

  1. Client ID Metadata Document — client hosts a JSON doc at an HTTPS URL, uses that URL as its client_id. AS validates. Modern MCP preference.
  2. Dynamic Client Registration (RFC 7591) — client POSTs metadata to registration_endpoint, gets a client_id back. [R6]
  3. Prompt the user — fall back to a manual client_id entry.

Step 4. Bind to the resource. The authorize request includes &resource=https%3A%2F%2Fmcp.example.com — this RFC 9728 parameter tells the AS to bind the issued access token's audience claim to that resource URI. Prevents confused-deputy: a token meant for MCP server A cannot be replayed at server B. [R8] [R9]

Why this matters in practice

The MCP spec doesn't invent anything new. It composes OAuth 2.1 (draft), PKCE (RFC 7636), Dynamic Client Registration (RFC 7591), AS Metadata (RFC 8414), and Protected Resource Metadata (RFC 9728) into a coherent discovery → register → authorize story. [R10]

🔄 Review from Lesson 4

PKCE · client generates verifier, sends challenge = SHA256(verifier) on authorize, reveals verifier on token exchange.

S256 · the only acceptable challenge method per RFC 9700.

OAuth 2.1 · PKCE is required for all clients using the authorization code flow.

Public clients · loopback redirect URIs (mobile), no embedded "secret", sender-constrained or one-time-use refresh tokens.
