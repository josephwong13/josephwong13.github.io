// 02 · ROLES

The Four Roles

01
Role 1
Resource Owner
The user — the only party who can grant access. Owns the data behind the resource server.
02
Role 2
Client
The third-party app requesting permission. Confidential = keeps a secret. Public = cannot (SPA, mobile).
03
Role 3
Authorization Server
Issues tokens after consent. Hosts /authorize and /token endpoints and the consent screen.
04
Role 4
Resource Server
The API holding protected data. Accepts access tokens. Often same vendor as AS — but logically separate.

// 04 · TOKENS

Access Tokens — Two Shapes

Opaque

Random string — no intrinsic meaning

RS calls AS introspection to learn token meaning. Easy to revoke — just delete server-side.

Authorization: Bearer xyz123
JWT · RFC 7519

header.claims.signature — self-contained

RS validates locally with AS public key. No round-trip — but harder to revoke before exp.

eyJhbGciOiJSUzI1NiJ9.eyJzdWIiOi…
Refresh Token

Long-lived credential (days–months)

Mint new access tokens silently without user interaction. Treat as high-value secret. Rotation required for public clients in OAuth 2.1.

Trade-offs

✓

Opaque: instant revocation

Delete from token store = immediate kill. No extra infrastructure.

✓

JWT: low latency

No introspection round-trip. Cached public key for validation.

⚠

JWT: revocation gap

No way to invalidate before exp without denylist or short TTL.

⚠

Refresh: high blast radius

Leak = unlimited token minting. Rotation required for public clients.

// 05 · PKCE

Proof Key for Code Exchange

⚠️

Authorization code interception attack

Malicious browser extension, mobile app hijacker, or confused URL handler reads the code from the URL bar. Without PKCE, the attacker redeems it — the client has no secret to prove legitimacy.

1

Generate verifier

code_verifier = BASE64URL(random(32))
2

Send SHA-256 challenge

code_challenge = BASE64URL(SHA256(verifier))
3

Redeem with verifier

POST /token
{ code_verifier: "..." }
S256

The only acceptable
challenge method

OAuth 2.1: PKCE required for all clients using auth code flow — public and confidential alike.

Security pitfalls (RFC 9700)

1 · Open redirect on redirect_uri

Prefix/wildcard matching lets attackers chain through your URL to exfiltrate the code.

✓ RFC 9700: exact string matching only

2 · Missing CSRF (no state)

Without state, attacker initiates flow returning to attacker's account (login CSRF).

✓ Always include random state per request

3 · Confused deputy

Token used legitimately on resources the user didn't consciously delegate.

✓ Narrow scopes + resource parameter (RFC 9728)

4 · Tokens in localStorage

XSS = full token theft. Use HttpOnly cookies or memory-only tokens.

✓ Memory tokens + refresh for persistence
// 07 · MCP COMPOSITION

MCP = OAuth 2.1 Composed

1

Unauthenticated request → 401 + WWW-Authenticate

RS returns 401 + WWW-Authenticate: Bearer resource_metadata="https://mcp.example.com/…"

2

Fetch Protected Resource Metadata (RFC 9728)

Contains authorization_servers[] — array of AS issuer URLs

3

Fetch AS Metadata (RFC 8414)

Discovers /authorize, /token, supported challenge methods

4

Run Auth Code + PKCE + resource parameter

&resource=https%3A%2F%2Fmcp.example.com binds token audience to this RS

MCP composes these RFCs

RFC 7636PKCE
RFC 9728Protected Resource Metadata
RFC 8414AS Metadata
RFC 9728resource parameter (audience)
RFC 7591Dynamic Client Registration

No new auth protocol — just careful composition of OAuth 2.1, PKCE, RFC 9728, and RFC 8414.
