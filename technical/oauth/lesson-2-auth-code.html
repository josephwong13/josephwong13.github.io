The Authorization Code Flow

Continuing the Google Calendar example. The todo app's backend can't just call accounts.google.com/oauth/authorize from its server — the user needs to type their password into Google's UI, not the todo app's. So we redirect the user's browser to Google.

The whole flow is a choreography of redirects: browser ↔ authorization server ↔ client backend ↔ resource server. By the end, the todo app has an access token and has never touched the user's password.

The happy path — 6 steps

Here's the full HTTP sequence as it would look for a confidential web client (todo app backend). [R1]

  1. User clicks "Connect Google Calendar" in the todo app. The todo app generates a random state value (for CSRF protection) and stores it in the user's session.
  2. Browser is redirected (HTTP 302) by the todo app to the authorization server's /authorize endpoint: 
    GET https://accounts.google.com/o/oauth2/v2/auth
    ?response_type=code
    &client_id=todo-app-123
    &redirect_uri=https://todo.example.com/callback
    &scope=https://www.googleapis.com/auth/calendar.readonly
    &state=xyz123
    &code_challenge=BASE64URL(SHA256(verifier))   ← Lesson 4 adds this
    &code_challenge_method=S256
  3. User ↔ Google authenticates (enters password / MFA) and sees the consent screen: "todo app wants to read your calendar". User clicks Allow.
  4. Browser is redirected back to redirect_uri with a short-lived authorization code: 
    GET https://todo.example.com/callback
    ?code=4/0AVMBsJ...           ← ~30s, single-use
    &state=xyz123                ← todo app verifies this matches
  5. Todo app backend exchanges the code for tokens at the token endpoint over a server-to-server HTTPS POST (never via the browser — the browser has the code, but the app has the client secret): 
    POST https://oauth2.googleapis.com/token
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code
&code=4/0AVMBsJ...
&redirect_uri=https://todo.example.com/callback
&client_id=todo-app-123
&client_secret=GOCSPX-...     ← confidential client only
&code_verifier=...             ← PKCE; Lesson 4
  6. AS → Todo app responds with: 
    {
  "access_token": "ya29.a0...",        ← ~1 hour
  "refresh_token": "1//0eX...",        ← weeks–months
  "expires_in": 3600,
  "token_type": "Bearer",
  "scope": "https://www.googleapis.com/auth/calendar.readonly"
}

The todo app now calls the Google Calendar API with the access token:

GET https://www.googleapis.com/calendar/v3/calendars/primary/events
Authorization: Bearer ya29.a0...
Why a code, not the token directly?

The whole flow exists because the browser is the only place where the user's password can be entered, but the browser is also the leakiest part of the system. Two redirect legs sandwich an opaque single-use code between browser and client. The actual token crosses only over a TLS-protected server-to-server call — never the browser. [R1] [R2]

RFC 9700 explicitly forbids returning access tokens in the URI fragment (the implicit grant) for exactly this reason. [R2]

Parameters you'll see in every authorize request

Required

response_type=code · client_id · redirect_uri · scope

Strongly recommended

state (CSRF token — RFC 9700 mandates CSRF protection on the client side; PKCE is one acceptable form [R2])

code_challenge + code_challenge_method=S256 — PKCE (Lesson 4). Mandatory for public clients and recommended for all in OAuth 2.1. [R3]

Discovery — getting the endpoints

Most clients don't hardcode https://accounts.google.com/o/oauth2/v2/auth. They fetch Authorization Server Metadata from a known discovery URL: [R7]

GET https://accounts.google.com/.well-known/oauth-authorization-server

The response is a JSON document listing authorization_endpoint, token_endpoint, code_challenge_methods_supported, and so on. This is exactly the mechanism MCP uses too.

The MCP connection

MCP · How this lesson maps

MCP's authorization spec describes exactly this flow as the required mechanism for HTTP-based MCP transports. [R9]

  1. MCP client discovers authorization server via the MCP server's 401 → WWW-Authenticate: Bearer resource_metadata="…" header.
  2. MCP client fetches Protected Resource Metadata (RFC 9728), gets the AS URL.
  3. MCP client fetches AS metadata (RFC 8414), learns the /authorize and /token endpoints.
  4. MCP client runs the authorization code flow — with PKCE (Lesson 4) and the resource parameter (RFC 9728 §2) binding the token to the MCP server's URL.
  5. MCP client uses the access token as Authorization: Bearer … on requests to the MCP server.

🔄 Review from Lesson 1

OAuth · protocol for delegated authorization that lets a third-party app act on your behalf without your password.

Authentication ≠ Authorization · OAuth is strictly about the latter (AuthZ = permission).

Resource Owner · the human (you) — the only party that can grant access.

Confidential vs Public client · Confidential = can hold a secret; public = cannot.

Resource Server · the API that holds the protected data and accepts access tokens.
