Why OAuth Exists

The problem. You click "Sign in with Google" on a todo app. The todo app needs to read your calendar. But you don't want to give the todo app your Google password — that would let it do anything with your Google account, forever.

You want the todo app to act on your behalf, but only within a narrow window: read calendar for the next hour, nothing else. And you want to be able to revoke that access without changing your Google password.

That's what OAuth solves. It's a protocol for delegated authorization — letting a third-party app act on your behalf without handing over your password.

The core distinction: authentication ≠ authorization

Authentication (AuthN)

"Who are you?"

Proving identity. Logging in with a username + password, or a magic link, is authentication. The answer is always a single bit of data: an identity assertion.

Authorization (AuthZ)

"What are you allowed to do?"

Granting permission to perform specific actions on specific resources. OAuth is exclusively about authorization — it never tells you who the user is, only what they have consented to let some client do.

Why this matters

You can layer identity on top of OAuth (OpenID Connect does this — Lesson 5 touches on it). But raw OAuth 2.0 only handles authorization. Confusing the two is the source of most OAuth design mistakes. [R1]

The four roles in OAuth

RFC 6749 (the original OAuth 2.0 spec) defines four cooperating roles. Every OAuth flow involves all of them, even if some are co-located. [R1]

Role 1 · Resource Owner

The user — you

The person (or system) that owns the data sitting behind the resource server. You, in the Google Calendar example. The resource owner is the only one who can grant access.

Role 2 · Client

The app that wants access

The third-party application requesting permission to act on the resource owner's behalf. The todo app. Clients are split into two types:

  • Confidential client — can keep a secret (server-side backend, native app with secure storage)
  • Public client — cannot keep a secret (browser SPA, mobile app where anyone can decompile the binary). OAuth 2.1 simplifies this to "has client credentials or doesn't". [R3]
Role 3 · Authorization Server (AS)

The trusted middleman

Issues tokens after the user consents. Google's auth server in the example. Hosts the /authorize and /token endpoints, and the consent screen.

Role 4 · Resource Server (RS)

The API holding the data

Accepts access tokens and returns protected data. Google Calendar API. The RS and AS are often run by the same vendor but are logically separate — and MCP keeps them strictly separate. [R9]

The big idea: delegation, not impersonation

The todo app never sees your Google password. Google shows you a consent screen listing the exact scopes requested (e.g., "Read your calendar"). You click Allow. Google gives the todo app a short-lived token that means "this user said yes to read-calendar until 3pm".

The token is not your password. It's a limited, revocable, scoped permission slip.

Common failure mode

Don't let the client log in as the user. Let it act on behalf of the user. The difference looks pedantic until you realize: with the password, the client can change the password, delete the account, and do everything the user can. With an OAuth token, it can only do what the granted scopes allow, until the token expires.

The MCP connection

MCP · How this lesson maps

The MCP authorization spec (2025-11-25) explicitly casts MCP clients, MCP servers, and authorization servers into these four roles: [R9]

  • MCP server = OAuth 2.1 resource server (accepts bearer tokens)
  • MCP client = OAuth 2.1 client (Claude Desktop, an IDE plugin, etc.)
  • Authorization server = third-party AS (Auth0, Keycloak, GitHub, etc.) — MCP explicitly allows the AS to live separately from the MCP server [R9]
  • Resource owner = the human who owns the data the MCP server protects

So when you connect an MCP client to a restricted MCP server, you're walking through exactly the same OAuth flow as "Sign in with Google" — just with a machine-readable scope instead of a human one.
