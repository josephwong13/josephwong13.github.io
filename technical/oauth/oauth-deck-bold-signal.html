The Problem

The todo app needs your calendar.

But you don't want to hand over your Google password. That would let it do anything with your account — forever.

Two very different worlds

❌ Password sharing

The app gets your password. It can change it, delete the account, do everything anything. Forever.

✓ OAuth delegation

A limited, revocable permission slip — scoped to "read calendar for 1 hour" — nothing more.

Core Distinction

Authentication ≠ Authorization

"

"Who are you?"

Proving identity — username + password, magic link, biometric. The answer is always a single bit: an identity assertion.

AuthN
"

"What may you do?"

OAuth's domain exclusively. The access token says: "this user consented to read-calendar until 3pm." Nothing about who the user is.

AuthZ
04
The Four Roles

Every OAuth flow has all four

01
Role 1
Resource Owner
The user — the only party who can grant access. Owns the data behind the resource server.
02
Role 2
Client
The third-party app requesting permission. Confidential = has a secret. Public = cannot keep one (SPA, mobile).
03
Role 3
Authorization Server
Issues tokens after consent. Hosts the /authorize and /token endpoints, and the consent screen.
04
Role 4
Resource Server
The API holding the protected data. Accepts access tokens and returns data. RS and AS often same vendor — but logically separate.

Access + Refresh tokens

Access token ~1h. Refresh token days–months. Token never crossed the browser.

{ access_token, expires_in,

🔑

The key insight: The browser carries the code — not the token. The token crosses only via a confidential server-to-server call. If the code is intercepted, it's useless without the code_verifier that only the legitimate client holds.

06
Tokens

Two shapes of access token

Opaque

Random string — no intrinsic meaning

RS must call the AS introspection endpoint to learn what the token means. Easy to revoke — just delete server-side.

Authorization: Bearer ***

(no info inside)
JWT

Self-contained: header.claims.signature

RS validates locally with AS public key. No introspection round-trip — but hard to revoke before exp. Requires short TTL or denylist.

eyJhbGciOiJSUzI1NiJ9.eyJzdWIiOi…

Trade-offs

Opaque tokens win on revocation

Server-side delete = instant kill. No infrastructure needed beyond token store.

JWTs win on latency

No introspection round-trip per request. RS validates signature with cached public key.

RFC 9700 preference

Introspection-based approaches preferred for sensitive workloads. JWTs need explicit revocation infrastructure.

Refresh Tokens

Long-lived credentials (days–months) used to mint new access tokens without re-prompting the user. High-value secrets — treat accordingly.

OAuth 2.1 · Public clients

Refresh tokens must be sender-constrained or one-time-use (rotation). One compromise = unlimited token minting.

08
PKCE

Proof Key for Code Exchange

⚠️

The attack: Authorization code interception

A malicious browser extension, mobile app hijacker, or confused URL handler reads the code from the URL bar. Without PKCE, the attacker redeems it — the client has no secret to prove legitimacy.

1

Generate code_verifier

Random 32-byte secret, Base64-URL encoded.

code_verifier = BASE64URL(random(32))
2

Send SHA-256 challenge

Challenge goes in the authorize URL. Verifier never leaves the client until token exchange.

code_challenge = BASE64URL(SHA256(verifier))
code_challenge_method = S256
S256

The only acceptable
challenge method

OAuth 2.1: PKCE is required for all clients using the authorization code flow — public and confidential alike.

09
Security Pitfalls

Common mistakes — and fixes

1

Open redirect on redirect_uri

Prefix/wildcard matching lets attackers chain through your URL to exfiltrate the code.

RFC 9700: exact string matching only
2

Missing CSRF (no state)

Without state, an attacker can trick a logged-in user's browser into starting a flow that returns the code to the attacker's account.

Always include a random state per request
3

Confused deputy

Client uses token legitimately, but on resources the user didn't consciously delegate.

Narrow scopes, clear consent, resource parameter
4

Tokens in URL fragments

Implicit grant leaked tokens via browser history, referer headers, extensions.

Auth code + PKCE for every client type
5

Refresh token reuse allowed

A compromised device with a reusable refresh token = unlimited access until revocation.

Rotation or sender-constrained for public clients
6

Tokens in localStorage

XSS = full token theft. HttpOnly cookies + CSRF tokens better. Best: tokens in memory.

Memory-only tokens + refresh for persistence
