PKCE & Public Clients

Lessons 1–3 assumed a confidential client with a server-side backend. The client posts its secret at the token endpoint, and that proves the redemption request is from the same client that received the code.

But a browser SPA cannot keep a secret — anyone can View Source. A mobile app's "secret" is in a binary anyone can decompile. What protects them?

That is the entire point of PKCE (Proof Key for Code Exchange, RFC 7636): prove the redemption request is from the same client, without using a shared secret. [R4]

The attack PKCE prevents

Authorization code interception

The classic SPA / mobile attack

Imagine a SPA running on https://todo.example.com/app that initiates the authorization code flow. The AS redirects back to that redirect URI with ?code=....

A malicious browser extension, a custom URL scheme hijacker (mobile), or simply a confused URL handler on a shared device can read the code from the URL bar — or grab it from browser history. Without PKCE, the attacker can then redeem the code at the token endpoint, because the client's "secret" (in a SPA, none) provides no barrier.

PKCE binds the code to the client that started the flow — even if the attacker steals the code, they cannot redeem it.

How PKCE works

The client creates a random secret, sends a derivative of it in the authorize request, and proves knowledge of the original secret when redeeming the code. [R4]

  1. Client generates a verifier 
    code_verifier = BASE64URL( random 32 bytes )
                // e.g. "dBjftJeZ4CVP-mB92K27uhxUJ0C1LprW..."
  2. Client derives a challenge 
    code_challenge = BASE64URL( SHA256(code_verifier) )
                 // e.g. "E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM"
  3. Send challenge in authorize request 
    GET https://accounts.google.com/o/oauth2/v2/auth
    ?response_type=code
    &client_id=todo-spa
    &redirect_uri=https://todo.example.com/callback
    &scope=calendar.readonly
    &state=xyz123
    &code_challenge=E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM
    &code_challenge_method=S256
    The AS stores the challenge alongside the issued code.
  4. Redeem code WITH the original verifier 
    POST https://oauth2.googleapis.com/token
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code
&code=4/0AVMBsJ...
&redirect_uri=https://todo.example.com/callback
&client_id=todo-spa
&code_verifier=dBjftJeZ4CVP-mB92K27uhxUJ0C1LprW...
    The AS recomputes SHA-256(verifier) and checks it matches the stored challenge. Only the original client has the verifier. The attacker's stolen code = useless.

S256 vs plain

two code_challenge_method values

plain — challenge = verifier (transmitted in the URL). If the attacker can read the authorize URL, they have the verifier. Useless for the threat model.

S256 — challenge = SHA-256(verifier). The verifier never crosses the network. RFC 9700 says S256 is the only acceptable method. [R2]

OAuth 2.1 makes PKCE required

"PKCE is required for all OAuth clients using the authorization code flow." Even confidential clients. The protection is cheap, has no downside, and stops both code-injection attacks and (as a bonus) authorization-code-replay CSRF. [R3]

If your client supports the authorization code flow and is NOT using PKCE, your implementation is out of date.

Other public-client requirements

Beyond PKCE
  • Loopback redirect URIs — mobile apps should claim http://127.0.0.1:PORT/callback (or private-use URI schemes), not fake https:// URLs they don't own (RFC 8252). [R5]
  • Refresh token rotation — public clients must use sender-constrained or one-time-use refresh tokens (OAuth 2.1). [R3]
  • No client secret — never invent a "secret" embedded in a SPA bundle. It's not a secret.

The MCP connection

MCP · PKCE is non-negotiable

MCP clients are typically public clients (Claude Desktop is a desktop app, IDE plugins are desktop apps, web-based MCP UIs are SPAs). RFC 9700 mandates PKCE for public clients. Therefore every MCP flow uses PKCE. [R2] [R9] [R11]

Concretely, every MCP authorization request includes:

&code_challenge=BASE64URL(SHA256(verifier))
&code_challenge_method=S256

And the token request includes the matching code_verifier. As Aembit notes, PKCE was originally written for mobile; MCP extends it as the universal public-client protection. [R11]

🔄 Review from Lesson 3

Access token · credential presented at the RS. Opaque (RS introspects via AS) or self-contained (JWT, RS validates locally).

Refresh token · long-lived credential used to mint new access tokens without re-prompting the user. Treat it as a high-value secret.

Scope · space-delimited permission unit; RFC 9700 mandates minimum-necessary scopes. Blast radius of a leaked token = its scopes.

Step-up authorization · a 403 with error="insufficient_scope" + new scope= in WWW-Authenticate asks the client to obtain additional consent.

Revocation · opaque tokens can be killed server-side instantly; JWTs need denylists or short TTLs.
