Tokens, Scopes & Refresh

The todo app now has an access token from Lesson 2's flow. Three new questions arise:

1. What's actually in that token? Can the todo app read its claims, or is it opaque?
2. What is the token allowed to do? Can we narrow the blast radius if it leaks?
3. It expires in an hour. Does the user have to re-consent every hour?

This lesson answers all three.

What is an access token?

Definition

An access token is a credential the client presents to the resource server

It's just a string. The format is up to the AS — the only requirement is that the RS can validate it. There are two widely-used shapes:

Opaque token

A random string with no intrinsic meaning. The RS calls back to the AS (or checks a local cache) to introspect it. Google uses opaque tokens for many of its APIs.

Authorization: Bearer ya29.a0AfH6SMB...   ← random, no information inside
JWT (JSON Web Token) · RFC 7519

Three Base64-URL segments separated by dots. The middle segment is a JSON claim set the RS can verify locally with a public key. Self-contained = no introspection round-trip.

eyJhbGciOiJSUzI1NiIs...        ← header (algorithm, key id)
.eyJzdWIiOiJ1c2VyXzEyMyIs...  ← claims (sub, scope, exp, aud, ...)
.dBjftJeZ4CVP-mB92K27uh...    ← signature

Header decodes to:

{ "alg": "RS256", "kid": "abc123", "typ": "JWT" }

Claims decodes to:

{
  "iss": "https://auth.example.com",
  "sub": "user_123",
  "aud": "https://mcp.example.com",
  "exp": 1735689600,
  "iat": 1735686000,
  "scope": "files:read files:write",
  "client_id": "https://app.example.com/oauth/metadata.json"
}
Choosing between them

JWTs look convenient (the RS doesn't need to call back), but they make revocation hard — the RS has no way to ask "is this token still valid?" without checking a denylist or accepting the JWT until exp. Opaque tokens are easier to revoke; just delete them server-side. [R2]

RFC 9700 prefers introspection-based approaches for sensitive workloads. [R2]

Scopes: least privilege by default

A scope is a string the AS understands as a permission. The client requests what it needs; the user consents to exactly that set; the AS records the granted set in the token's claims.

Examples by domain
Google:    https://www.googleapis.com/auth/calendar.readonly
GitHub:    repo  read:user  workflow
Slack:     channels:read  chat:write  files:read
MCP:       files:read  files:write  user:profile

Scopes are space-delimited, opaque strings — each AS defines its own vocabulary. There is no central registry. [R1]

RFC 9700: scope = the security boundary

"Access tokens must be restricted to the minimum scope necessary." If your client only reads, request only the read scope — not *, not a wildcard. Broad tokens that leak are catastrophic. [R2]

Refresh tokens

The problem with short-lived access tokens

If access tokens live an hour and the user is active all day, something has to extend the session without re-prompting them every hour.

That's the refresh token's job. It's a long-lived credential (days to months) that the client uses to mint new access tokens at the token endpoint — with no user interaction.

POST https://auth.example.com/token
Content-Type: application/x-www-form-urlencoded

grant_type=refresh_token
&refresh_token=1//0eX...
&client_id=todo-app-123
&client_secret=GOCSPX-...

The AS returns a fresh access token (and optionally rotates the refresh token).

Refresh tokens are secrets

Treat refresh tokens more carefully than access tokens. An access token leak is bounded by exp (often < 1h). A refresh token leak = unlimited new access tokens until revocation. [R2]

OAuth 2.1 mandates: refresh tokens for public clients must be either sender-constrained or one-time-use (rotation). The leak surface is too large otherwise. [R3]

MCP · Scope challenges & step-up

MCP servers can ask for more scope mid-session. From the spec: [R9]

HTTP/1.1 403 Forbidden
WWW-Authenticate: Bearer error="insufficient_scope",
                         scope="files:read files:write user:profile",
                         resource_metadata="https://mcp.example.com/.well-known/oauth-protected-resource"

If the MCP client tries a tool call that needs files:write but only has files:read, the RS rejects with 403 and lists the scopes it would have accepted. The client should then run step-up authorization — re-engage the user to consent to the additional scope.

Revocation

RFC 7009

Some ASes expose a /revoke endpoint. Either the user revokes via the AS account dashboard, or the client signals "I'm done with this token." Revocation of an opaque token is cheap. Revocation of a JWT before its exp requires extra infrastructure (denylist or short-lived JWTs).

Why a code (not the token) crosses the browser · the browser is the leakiest part of the system; the code is opaque, single-use, and expires in ~30 s.
