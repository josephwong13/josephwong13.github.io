Why OAuth Exists

The Core Problem

📅

You click "Sign in with Google" on a todo app. The todo app needs to read your calendar. But you don't want to give the todo app your Google password — that would let it do anything with your account, forever.

❌ Password sharing

The app gets your password. It can change it, delete the account, do everything you can. Permanent, irrevocable access.

✓ OAuth delegation

A limited, revocable permission slip: "read calendar for 1 hour, nothing else." Token-based — no password ever shared.

The Four Roles

Role 1
Resource Owner
The user — the only party who can grant access. Owns the data behind the resource server.
Role 2
Client
The third-party app requesting permission. Confidential = keeps a secret. Public = cannot (SPA, mobile).
Role 3
Authorization Server
Issues tokens after consent. Hosts /authorize and /token endpoints and the consent screen.
Role 4
Resource Server
The API holding protected data. Accepts access tokens. Often same vendor as AS — but logically separate.

Authorization Code Flow

The Happy Path — 6 Steps

1

User clicks "Connect Google Calendar"

Client generates random state value (CSRF protection) and stores it in the session.

2

Browser redirects to AS /authorize

response_type=code, client_id, scope, state, PKCE challenge.

?response_type=code&code_challenge=SHA256(verifier)&state=xyz123
3

User authenticates + consents

Enters password at Google's UI. Sees exact scopes. Clicks Allow.

4

Browser receives short-lived CODE

~30s expiry. Single-use. Opaque — no information inside.

GET /callback?code=4/0AVMBsJ…&state=xyz123
5

Backend exchanges code → token (server-to-server)

Client secret and code_verifier never touch the browser.

POST /token { code_verifier: "dBjftJeZ…" }
6

Access + Refresh tokens returned

Access token ~1h. Refresh token days–months. Token never crossed the browser.

{ access_token, expires_in, refresh_token, scope }

Token Types & Scopes

Access Tokens & Least Privilege

Two shapes of access token

Opaque

Random string. RS must introspect with AS. Easy to revoke — just delete server-side.

JWT (RFC 7519)

Self-contained: header.claims.signature. RS validates locally — no round-trip. Harder to revoke before exp.

Refresh Tokens

Long-lived (days–months). Mint new access tokens silently. Treat as high-value secrets. OAuth 2.1: rotation required for public clients.

PKCE · RFC 7636

Proof Key for Code Exchange

Authorization code interception attack

A malicious browser extension or mobile hijacker reads the code from the URL bar. Without PKCE, the attacker redeems it — the client has no secret to prove legitimacy.

1

Generate verifier

code_verifier = BASE64URL(random(32))
2

Send SHA-256 challenge

code_challenge = BASE64URL(SHA256(verifier))
3

Redeem with verifier

POST /token { code_verifier: "..." }

OAuth 2.1: PKCE required for all clients — public and confidential alike.
