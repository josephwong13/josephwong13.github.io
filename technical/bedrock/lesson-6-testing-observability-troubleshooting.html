Testing, Observability & Troubleshooting

Scenario: After deploying a new Claude 3.5 Sonnet prompt, customer satisfaction scores drop. The old model seemed fine in testing. A rollback is triggered. Now you need to understand why — and build a testing pipeline that catches this before production. This lesson is about the GenAI-specific testing and observability stack that traditional software engineering doesn't have.

Bedrock Model Evaluations

D5 SKILL 5.1.2

Automated, LLM-as-Judge, and human preference evaluations

Automated evaluations — compare model outputs against a reference answer using a scoring rubric (relevance, factual accuracy, coherence). Fast, reproducible.
LLM-as-Judge — a high-capability model (Opus) evaluates a lower-capability model's outputs against a prompt. Most cost-effective for subjective quality. Run nightly against a golden dataset.
Human preference — A/B evaluation by human evaluators. Slowest but most accurate for tone, nuance, and domain-specific quality. Required for final pre-launch sign-off.[R16]

A/B + CANARY

A/B testing and canary deployments of FM prompts

A/B test: route 50% of traffic to prompt variant A, 50% to variant B. Measure business metrics (CSAT, conversion). Minimum 3–5 days for statistical significance given FM variance.
Canary: deploy new model/prompt to 5% of traffic, monitor for 24h, auto-rollback if error rate exceeds threshold. Use CloudWatch Anomaly Detection on token-count and latency metrics.[R16]

Regression testing for FM outputs

D5 SKILL 5.1.4

Continuous evaluation pipelines

Store a golden dataset — a curated set of query/expected-response pairs. Run against every model/prompt change. Metrics: % of outputs within acceptable similarity threshold to golden answer (e.g. embedding cosine similarity > 0.85). If drop > 5%, block deployment.[R16]

D4 SKILL 4.3.6

Output diffing — response consistency

Run the same query 3–5 times. Compare outputs for: consistency of factual claims, tone stability, structural adherence (JSON schema). High variance across runs on identical input = unstable model configuration. Tune temperature or switch models.

CloudWatch for Bedrock

OBSERVABILITY

Bedrock-specific CloudWatch metrics

InvocationLatency — end-to-end model invocation time (ms). Spike = model throttling or queue depth.
InputTokenCount / OutputTokenCount — per-invocation token volumes. Aggregate for cost attribution by IAM principal or API key.
InvocationErrors — 400/429/500 errors. 429 = throttling; consider Provisioned Throughput.
ModelInvocationLogs — per-request logs with input/output (enable selectively for PII/compliance).[R1]

ANOMALY DETECTION

CloudWatch Anomaly Detection on Bedrock metrics

Train a baseline on 7 days of normal traffic. Anomaly Detection alerts when: token burst patterns appear (potential prompt injection), response latency drifts, output token count drops unexpectedly (model truncating responses), or error rate spikes. Set alert on bedrock:InvocationError and bedrock:InvocationLatency.

X-Ray for prompt observability pipelines

D5 SKILL 5.2.5

X-Ray trace propagation through prompt pipelines

When a prompt flows through: API GW → Lambda (pre-processing) → Bedrock → Lambda (post-processing) → client, X-Ray traces the full chain. Use subsegments to annotate each stage's input/output. Identifies which stage introduced latency or corruption. CloudWatch Logs for prompt confusion diagnosis at the Lambda pre-processing stage.

Retrieval quality testing

D5 SKILL 5.1.6

Retrieval metrics — relevance, context matching, latency

Relevance scoring — for each query, human-annotate or LLM-judge rate retrieved chunks as: fully relevant / partially relevant / irrelevant. Target > 80% fully relevant.
Context matching verification — confirm retrieved chunks contain the answer to the query (not just high embedding similarity). High similarity ≠ correct answer.
Retrieval latency — vector search latency should be < 50ms p99. If higher, check index size, embedding model, or vector DB instance type.

GenAI-specific troubleshooting patterns

D5 TASK 5.2

Common failure modes and fixes

Context window overflow — diagnose with token estimation before calling. Fix: context pruning, reduce chunk count, use a model with larger context.
Hallucinations — diagnose: low retrieval relevance + no grounding in context. Fix: improve KB chunk quality, add guardrails + KB configuration.
Semantic drift — diagnose: embedding similarity between current outputs and golden dataset drops over time. Fix: retune model or update prompt.
Prompt injection — diagnose: anomalous token burst in input (injected prompt). Fix: input sanitization Lambda + Guardrails.
Vectorization issues — diagnose: retrieved chunks are semantically wrong despite correct documents. Fix: re-embed with different chunking strategy or embedding model.

🔄 Review from Lesson 5

Prompt caching — caches repeated context at a reduced fee vs full token pricing. Semantic caching extends this to paraphrase variations.[R17]

Provisioned Throughput — by-Model-Units commits hourly capacity; by-Tokens pay-per-use. Breakeven ~40% utilization.[R15]

Tiered model routing — cascade from Haiku to Opus based on complexity; reduces cost 60–80%.[R1]
